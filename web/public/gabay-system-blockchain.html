01 · The application

What is ANHS Vote?

This is a digital system for electing student leaders. It helps COMELEC/admin prepare elections, register voters, provide voting access, and view results. Students use assigned tokens instead of creating their own accounts or crypto wallets.

UserSystem activities
Admin / COMELECEmail/password login; student records and CSV import; positions and candidates; token generation; publishing, opening, and closing elections; reports and ledger verification.
Student / voterToken login; choosing a candidate or abstaining for each position; review; final submission; receipt.
Public visitorElection status, participation, announcements, permitted results, and receipt-code lookup. These do not require admin login.

CSV import detects common headers and file formats. Column mapping, defaults, and an editable preview support other layouts. Preview records before saving; the system does not invent missing LRNs.

Purpose: improve election administration and provide blockchain evidence for recorded candidate votes. Election organizers remain responsible for identity checks and proper token distribution.

02 · Start here

What is blockchain in simple terms?

Think of a shared record book of transactions. Many computers in the network follow the same rules to agree on which records are valid. Cryptography helps verify authorization and links between records. It is not an ordinary file that someone can simply edit on a laptop to replace the results.

In this project, the student election app sends requests. The Solana network runs the program rules and records valid changes. The school website itself is not the entire blockchain.

TermSimple explanationIn this project
Blockchain / ledgerA shared record of network transactions and state.Solana is the network used by the election program.
TransactionA signed request that may contain multiple instructions.A submission batch may contain several candidate-vote instructions.
InstructionA command to a program.For example, cast_vote for one position.
Program / smart contractCode that enforces rules on the blockchain.The Rust/Anchor voting program checks registered tokens, valid candidates, and open elections.
Account / stateData stored at a blockchain address.Election, Position, TokenRecord, and VoteRecord accounts.
ValidatorA computer participating in network processing and consensus.Solana validators; student laptops are not automatically validators.
RPCAn API the app uses to communicate with the blockchain.Backend → Solana RPC → network.

Solana state is stored in accounts; transactions are signed requests containing instructions. Sources: Solana account structure and Solana transactions.

If asked, “What is blockchain?”

“Blockchain is a shared record system verified by a network. In our project, we use it to enforce voting rules and provide transaction evidence and vote counts that can be checked on Solana.”

03 · System architecture

How do the parts connect?

  1. Browser / ReactThe interface used by admins, students, and public visitors.
  2. Backend / ExpressChecks login, eligibility, ballots, and submissions. Connects to SQLite and Solana.
  3. SQLite + SolanaSQLite handles administration; Solana programs/accounts handle on-chain elections and votes.

Stack: React + Vite for the frontend; Node.js + Express for the backend; SQLite for local data; Rust + Anchor for the Solana program. The backend client uses the Anchor library to call the program.

Who signs? The server wallet is the authority and fee payer in the current implementation. Students use voting tokens to access the app; they do not sign directly with their own Solana wallets.

The appropriate description is a hybrid application with a blockchain component. The underlying network is decentralized, but the app still has a central backend and election authority. Using blockchain alone does not make the whole app fully decentralized.

05 · The network

Why Solana Devnet?

The backend defaults to https://api.devnet.solana.com. The reviewed configuration had no alternative RPC_URL override, so it used Devnet. The Anchor development configuration includes a localnet entry, but the running web application follows the backend RPC setting.

Devnet is for application development and testing. It uses test SOL and may undergo ledger resets. Describe the current deployment as a development/prototype setup; do not promise permanent production election records on Devnet. Source: Solana clusters and endpoints.

Consensus: PoS and PoH

Solana uses Proof of Stake (PoS) consensus. Proof of History (PoH) helps order events; it should not be described as a separate consensus mechanism replacing PoS. Sources: Solana staking/consensus explanation and Solana whitepaper.

A student vote for a candidate differs from a validator consensus vote for blocks. COMELEC/server authority controls election operations; this does not make Solana a Proof of Authority network or a private school blockchain.

Why is there a SOL balance?

Network transactions incur fees, and creating on-chain data accounts requires a minimum balance. The server wallet pays in the current app, so students do not need SOL wallets. Dashboard cost estimates come from the project code and are not guaranteed final costs. Sources: Solana fees and account balances/storage.

06 · From preparation to receipt

Step by step: how does voting happen?

  1. Prepare students. Admin adds/imports records and checks who is active and eligible.
  2. Prepare the ballot. Admin adds positions/candidates and generates assigned eight-character voting codes. Database token generation and on-chain token registration are separate steps.
  3. Publish the election. The backend creates Election/Position accounts and registers eligible unused token hashes. A frozen mapping connects local candidate IDs to on-chain candidate indices.
  4. Open voting. The backend checks token registration before opening. In the usual flow, on-chain status moves from Pending → Open → Closed.
  5. Token login. The backend checks the code, active student, unused token, and open election. It creates a voter session tied to the current election.
  6. Candidate selection. Voters choose a candidate or abstain for each position. Draft choices stay in the browser tab and are not yet on-chain votes.
  7. Review and final submission. The backend validates all positions and candidate indices. The server wallet signs and sends non-abstain vote instructions.
  8. Chain validation. The voting program checks the authorized signer, registered token, open status, valid option, and unique token-position vote record before updating the tally.
  9. Completion and receipt. Once all required batches finish, the database marks the token/student as used/voted and creates a receipt. It includes all transaction signatures for non-abstain votes.

Once closed: the current program cannot reopen the same election. Status only moves forward; Pending → Closed is also possible when closing before opening. The archive/new-election operation uses a new election ID for the next election.

07 · On-chain rules

How are duplicate votes prevented?

A Program Derived Address (PDA) is generated from the program ID and seeds. Identical inputs produce the same address. Source: Solana PDA documentation.

For a candidate vote, the program creates a unique marker using:

VoteRecord address = program + position address + token hash

If the same token votes again for the same position, it attempts to create an account at the same address. That record already exists, so duplicate creation is rejected and the tally is not incremented again.

RuleImplementation
Authorized operationThe signer must match the election authority.
Registered tokenA token PDA must exist for the election and token hash.
Open electioncast_vote requires Open status.
Valid candidateThe candidate index must be within that position’s candidates.
One vote per positionA unique VoteRecord PDA for each token-position pair.
One completed app submissionA local used flag and unique receipt per election/token hash.

Nuance: on-chain protection means one vote per token per position. Full submission completion, abstain tracking, and student eligibility also depend on backend/database rules. The program cannot establish the real identity of the person holding a token.

The reviewed source has no direct set_votes or edit-tally instruction. This does not mean all changes or abuse are impossible: server/authority security and the deployed program’s upgrade policy matter.

08 · Three different identifiers

Voting tokens, hashes, sessions, and signatures

ItemWhat is it?How to remember it
Voting tokenAn assigned eight-character app access code.A ticket to the voting page. It is not an SPL token or cryptocurrency.
Token HMAC/hashThe backend derives a SHA-256 HMAC using a secret pepper and normalized code.An identifier for chain registration/votes. It does not encrypt candidate choices.
Voter session JWTA signed login session with a voter role/election ID; current expiry is two hours.Proof to the API that the tab completed token login. Separate from the original voting code.
Transaction signatureThe identifier/signature of a signed Solana transaction.Used to locate a chain transaction. One receipt may have multiple signatures.
Receipt codeA random twelve-character reference stored in SQLite.Looked up at /verify. It is not a transaction signature.

Hashing alone does not establish anonymity. The voting code is locally associated with a student. Blockchain instructions contain token hashes and candidate indices. Access to records and server secrets may link identities to choices, and linked transactions may reveal selections. The current version offers verification/transparency with privacy limitations.

09 · Concrete example

Example: one voter, three positions

This is a fictional example. Four tokens are registered, and the first student is submitting.

PositionChoiceEffect
PresidentAna+1 to Ana’s President tally.
Vice PresidentAbstainNo candidate-vote instruction for this position.
SecretaryPedro+1 to Pedro’s Secretary tally.

Result: 1 completed submission, 2 candidate-vote instructions, and 1 receipt. Turnout = 1 ÷ 4 × 100 = 25%. Position vote totals may differ because voters can abstain.

Abstaining for all positions still completes a submission and marks the local token as used, but sends no candidate-vote transaction. A local all-abstain receipt is the app’s evidence. Not every receipt has a blockchain transaction.

Public candidate percentages use candidate votes for that position as their denominator. If Ana receives the only President vote, her position share is 100% even though overall turnout is only 25%.

10 · Evidence and recovery

What do receipts and the ledger prove?

/verify looks up receipt codes in the local database and shows available transaction links. A “valid receipt” means the record was found; it is not automatically independent proof of every ballot choice or secrecy.

Admin → Ledger → Verify checks counts and transaction statuses. Results are PASS, WARNING, FAIL, or N/A. Signature confirmation/status comes from the RPC. Status API source: getSignatureStatuses.

  • PASS: the specific consistency check passed.
  • WARNING: evidence is incomplete/uncertain, a mismatch needs review, or RPC history is unavailable.
  • FAIL: the check found an inconsistency or transaction error.
  • N/A: not applicable, such as a chain signature for an all-abstain receipt.

If the connection is interrupted

The project batches up to six positions. Seven positions with candidate choices may require two transactions: the first six, then the seventh. This is an app batching choice, not a universal six-position Solana limit.

Each transaction is atomic: if one instruction fails, that transaction’s state changes revert. Source: Solana transactions. A ballot spanning multiple batches is not one atomic transaction.

Local batch signatures and transaction lifetimes are recorded before broadcast. Retries check previous signatures and confirmed instruction data. Confirmed batches are not simply repeated; pending transactions may need more time, and uncertain evidence may need escalation. Browser selections remain locked while submission is pending to support safe retries.

If completion succeeded but the response was lost, the API can return the existing receipt. “The success screen did not appear” does not necessarily mean “no vote reached the blockchain.”

11 · Honest explanation

What should you clarify during the defense?

Avoid sayingMore accurate explanation
“All data is on the blockchain.”Hybrid: administration/receipts in SQLite, election rules and candidate tallies on Solana.
“Votes are 100% anonymous and encrypted.”Tokens are HMAC-derived, but choices may appear in transactions and identities may be linked in the backend.
“The app is fully decentralized.”It still has a centralized server, local database, and server signing wallet.
“Nobody can cheat.”Rules and evidence still require trusted eligibility checks, token handling, server/key security, and review.
“Devnet records last forever.”Devnet is for testing and may reset; backups and production planning are needed.
“Valid receipt means everything was proven.”Lookup proves local existence; ledger checks have a limited scope.
“One click always means one atomic ballot.”Larger ballots can use multiple transaction batches.
“The schedule automatically opens/closes voting.”The schedule is display metadata; admin chain-status operations control voting in the reviewed implementation.

Solana programs may be upgradeable if an upgrade authority exists. This guide did not inspect the deployed program’s actual upgrade-authority state, so it does not claim the program is permanently immutable. Source: Solana programs and upgrades.

If SQLite is lost: chain tallies may still be readable when the network/accounts are available, but they do not automatically restore student associations, receipt-code mappings, administrative metadata, or batch-recovery records. Chain evidence and proper database backups are both needed.

This document explains reviewed source and local configuration. It is not an independent security audit or proof that this exact source matches deployed bytecode. No new votes or blockchain transactions were sent while preparing it.

12 · Say it in your own words

A script you can practice

Short introduction — about 45–60 seconds

“Our project is ANHS Vote, a web-based election system for the SSLG of Agusan National High School. It has an admin portal for students, candidates, tokens, and election management; token login and digital ballots for voters; and public results and receipt verification.

We use Solana Devnet. Student information and receipts are in a local database, while election setup and candidate vote counts are on the blockchain. When a voter submits, the backend checks eligibility and choices, then the server wallet sends the vote transaction. A program rule allows one vote per registered token for each position.

The blockchain provides verifiable transaction records and controlled tally updates. The implementation is still a hybrid prototype, and we do not claim it is fully anonymous or fully decentralized.”

Longer explanation — three parts

  1. Problem and users: “We want to improve student election management. Admin prepares records; voters make selections; the public sees permitted election information.”
  2. Actual blockchain flow: “We publish election setup, register token hashes, and open the election. Final submission calls the voting program through the server. The program checks open status, token, candidate, and unique vote record before incrementing the candidate tally.”
  3. Verification and limits: “Receipts and Explorer links provide chain evidence. A local database and server wallet remain, and choices may be linked. Devnet is a testing environment, so privacy improvements and production review are needed before using this as production election infrastructure.”
Remember: problem → flow → evidence → limits.

Start with who uses the system, what happens to a vote, and where to find evidence before introducing long acronyms.

13 · Walkthrough

How can you demonstrate the system while explaining?

  1. Public page: show the election title/status, participation, and results. Explain which values are chain tallies and which are local receipt counts.
  2. Admin → Students: show records and CSV preview using fictional/demo data.
  3. Admin → Candidates/Tokens: explain the ballot and assigned access codes. Do not show real students’ usable voting codes.
  4. Admin → Blockchain: show configured wallet/program/election addresses, registration status, and SOL estimates. Publishing and opening are separate actions; database tokens alone are insufficient.
  5. Voting: if a demo election is prepared, use a demo token, select choices, review, and submit. Explain that choices remain drafts before submission. An actual demo submission changes state on the selected network.
  6. Receipt and Explorer: show the code and every available transaction link. Point out Devnet, transaction success/status, and program/instruction/account evidence. Reading candidate indices may require decoding.
  7. Ledger: run consistency checks and explain PASS/WARNING/FAIL/N/A. An all-abstain demo normally has no chain signature.

If the demo election is closed: show archived results or prepare a new demo election through the existing workflow. The current program cannot reopen a closed election. Finishing a presentation does not require closing an ongoing election.

14 · Panel Q&A

Possible questions and accurate answers

1. Why keep a database when you have blockchain?

“They serve different purposes: SQLite stores identities, eligibility, app login, and receipts; blockchain stores published elections and candidate tallies. The project uses a hybrid design.”

2. Why blockchain instead of only a database?

“It provides on-chain rules and network transaction evidence separate from the local display/database. It adds complexity, network dependency, and costs, and does not replace administrative responsibilities.”

3. How do you know the voter is a real student?

“That depends on verified student records and proper token assignment/distribution. Blockchain validates token identifiers and rules; it does not independently verify student identity.”

4. What if a token is passed to someone else?

“Anyone with access to the code may use it. The system does not automatically recognize the true owner, so controlled distribution and token privacy matter.”

5. How do you prevent double voting?

“Local used-token/receipt rules and a unique on-chain VoteRecord protect each token-position pair. A duplicate vote cannot create the same vote account again.”

6. Can people see which candidate was selected?

“Choices may be visible in transactions. Student LRNs/names are not directly sent in cast-vote instructions, but backend records and token identifiers allow linkage. We do not claim a secret-ballot guarantee in this version.”

7. Does every student need a crypto wallet?

“Not in the current implementation. Voters use token login, and the server wallet signs and pays fees.”

8. Does the student pay?

“There is no direct wallet payment in the voter UI. The server wallet covers network/account costs, using test SOL on Devnet.”

9. Are all abstentions on the blockchain?

“No candidate instruction is sent for an abstained position. An all-abstain submission has only a local completed receipt and no candidate-vote transaction.”

10. What happens if submission returns an error?

“Keep the same choices and use the existing retry/recovery flow, since a batch may already be confirmed. The backend checks signatures before resending.”

11. Can the admin change vote counts?

“The reviewed program has no direct edit-tally instruction, and published setup operations are locked in the app. Server signing authority and possible program upgrades remain trust considerations; we do not promise immunity to compromised authority.”

12. Is this ready for a production election?

“The configured network is Devnet, with identified privacy and centralization limits. Deployment, access/key management, backups, privacy, and security need review before claiming production readiness.”

15 · Rehearse

How can you learn the explanation?

  1. Read sections 1–6. Explain one student vote to a friend without looking at notes.
  2. Draw: Browser → Backend → SQLite / Solana. Explain the request or data at each arrow.
  3. Distinguish four items: voting code, session JWT, receipt code, and transaction signature. Do not call them all the same “token.”
  4. Use section 9’s example. Why is there one submission but two candidate votes? Why do turnout and candidate percentages differ?
  5. Practice the Q&A. Answer briefly, then give a concrete example.
Cheat sheet — six lines to know
  • Purpose: school election management and token-based voting.
  • Architecture: React → Express → SQLite + Solana.
  • Network: Solana Devnet for the current development setup.
  • Signer: server wallet; students do not need their own wallets in this flow.
  • Protection: registered token, open status, valid candidate, unique token-position vote record.
  • Limits: hybrid design, no anonymity guarantee, local receipts/abstentions, and Devnet reset risk.

If you do not know an answer: “What we verified in the current implementation is ____. We have not verified ____ yet, so I cannot claim that.” This is clearer and more credible than making an incorrect technical claim.
